# 512更新checkpointでの入力形式修正の影響

学習せず同じ重みで、元の32件DEVについて本文・順序・EOSを保ったまま履歴先頭の人間をrole3に統一した。19件の3/4が全履歴と返答roleを通して一対一に入れ替わり、13件は同一。TRAIN文書は元からBOS1/role3で開始しており、TRAIN/Tokenizerは変更しない。packed DEV64窓は文書内断片であり、架空のBOSを挿入せず同一入力のまま比較した。

| 32件の指標 | 小型 修正前→修正後 | 中型 修正前→修正後 |
|---|---|---|
| 正解返答本文NLL/token | 6.023540722 → 6.021078218 | 5.751612155 → 5.748050555 |
| 無修正全文が変化 | 1/32 | 0/32 |
| 実際にEOSを生成 | 32/32 → 32/32 | 32/32 → 32/32 |
| 機械的4gram反復 | 0/32 → 0/32 | 2/32 → 2/32 |

小型の変更はv2-dev-026の短い相槌の変化のみ。形式修正により予測値はわずかに変わるが、形式不一致が内容不足の主原因だったとは言えない。中型の不自然な反復を含む全文も同一で、本文の能力改善を形式修正の成果としない。

追加の内容必須24件DEVは、元の32件とは文書が重ならず、TRAINとの話者・文書・完全な履歴＋返答・返答本文の完全重複も0。小型512の全文は「そうなんですね。」22件と「そうなんです。」2件。中型512は同じ相槌22件と「そうなんです。」1件、「おお食べます。」1件。EOS到達は両24/24で、短く終了すること自体は具体的な回答を生成できた証拠ではない。内容の判定は別途全文を読んで行い、NLLや反復検出だけで成功を判定しない。

修正前の結果は上書きせず元のevaluation/に保存し、今回の全出力とtoken列はepoch1/evaluation/、32件の修正前後の全文対照はevaluation-comparison.jsonに保存した。新しい24件は全てDEVであり、封印TESTではない。旧厳格な採用基準を変更していない。
