# 既存会話の再配分：実データ準備・数値監査と開始判断

メイン単体でPR92〜97と保存済みの研究を引き継いだ。新規収集やモデル拡大へ脱線せず、RealPersona TRAINの分布、固定標本、JMultiWOZの未完40会話、同じ初期状態でのデータ配分比較、保存容量と数値状態を検証した。**optimizer更新0、本学習・正式採用No-Go。探索的な状態変更比較も現段階では未承認。** 公開モデル・サイト、旧23DEV、Git履歴・元checkpointを変更しない。

## 既存TRAIN内の応答

全TRAIN5986会話/180006発話、異話者隣接174020組を集計。疑問符の後の発話37072、理由要求語692、比較要求語1253、相談要求語970、返答の因果表現27559、複数文末記号74761。これらは重複する構文proxyで、意味成立や正しい返答の認定数ではない。長さやregexだけで内容ありとは判定しない。

内容を見る前にSHA固定した20会話を全発話読解した。全20に具体的な質問・回答・追加質問のやり取りがあったが、全発話が内容ある返答という意味ではない。仕事、料理、旅行、キャンプ、天候対策、ゲーム、音楽、スポーツ、買い物等を含む。個人の健康、家族、未検証の健康一般論等がある6会話を新しいfocus候補から保留し、残る14会話を条件付きの配分候補とした。生の全文は再公開せず、ID・SHA・具体的な抽象理由を保存。標本の割合を母集団の意味的内容率に置き換えない。

重要なのは、既存TRAINに具体的な会話が存在しないわけではないという点。一方、14会話全体を重くしても内部の相槌も増える。現標本だけではfocusと全体の返答単位の内容密度差、topic・文体の偏りを検証できていない。人間同士の経験をAI自身の属性として正解化せず、現段階のhuman-dialogue language modelingとassistant応答を区別する。

## JMultiWOZ40会話と活用条件

旧PLAN/sample-receiptの40IDを引き直さず、保存された全発話を読解した。全40に具体的な案内・条件確認・変更・参照がある。予約人数/泊数/時刻の変更、先に紹介した施設への代名詞参照、不明値の明示は有用。一方、空の末尾USER発話が3会話にあり、真の会話終了とは扱えない。00:00～00:00の営業時間や徒歩0分、無料と有料が併記される値、希望を早合点して外す例も確認した。

原典DBの値はSHA/フィールド名だけが準備済み資料に残り、今回は元の値を復元して照合していない。したがって**40会話の読解は完了、DB依存の事実正確性は保留**。現在の料金/天気の真実性や実際の予約能力を認定していない。3,646会話全体の品質合格ともしていない。空発話を除去して原文やEOSを事後的に都合よく直してはいない。

旧23DEVと話者/familyで接続する全件隔離を維持し、TRAINへ戻していない。既存の露出済みDEVを診断専用とする新系列は理論上設計できるが、それだけで独立性は回復しない。新しい外部評価でspeaker・source・family独立性を監査し、旧23の成績を採用・一般化の証拠から外す別条件の事前固定が必要。独立した提供者や正式な母語話者評価は未確保なので、新系列の復帰も未承認。旧条件を上書きしない。

活用方法は分ける。(1)可視履歴だけで答えられる問い返し・条件の要約・参照解決、(2)active_entity/book_resultの原典snapshotを明示的に入力する応答、(3)基盤原文としての人間タスク会話。(2)は入力形式の変更なので今回の配分比較へ混ぜない。検索結果を見せず施設名/番号/天気/予約成功を無条件の正解にしない。

## 実装した配分schedule

初期medium3470/Adam/RNG、独自3997BPE、context256、4slot、全causal CE、clip1、継承LR3e-5を共通にする候補。controlは元TRAIN全窓から有効長で対応付け、treatmentは同じ2slotとfocus側2slot。窓の元token列を使い、偽BOS/EOS・文書結合・切り直しはしない。各arm内の窓重複0、有効target数とslot長は両条件で一致する。

実際に作成できたscheduleは各14保持更新/11400targets、focus28窓・5840targets。予定200/2048を完了数や実現可能数へ流用しない。これは小さい条件付き実現可能性scheduleであり、十分な言語学習量ではない。対照は元TRAIN全体からの長さ層別抽出で、歴史的shuffleの続きを再現したものではない。最初のsample除外control案は比較対象として不適切なのでsuperseded-source-excluded-controlへ保存し、現在案と混算しない。

run_comparison.pyにfull state/atomic保存を含む実行gateを実装したが、EXPERIMENT.jsonは更新を明示的に禁止。新runnerの更新後中断・再開・replayと、実更新ledgerの検証は未実行。旧sampler履歴と新しいallocation cursorを区別する。構文検証だけで再開可能と主張しない。

## 数値・保存の実測

Git blobとbyte一致を確認した古いcheckpoint作業コピー6個だけをsparse省略し、空きを99684352→473198592bytesへ回復した。原本blobと履歴は保持し復元可能。削除した原checkpointは0。STORAGE_RECOVERY.jsonに各path/blob/sizeと実際の回収量を保存。

小さいfsync/replace試験に加え、実checkpointをGitからSHA検証してRAMへ復元し、実モデルで現在条件4 forward/backwardを実行。loss・全勾配・clip後normの有限性を確認し、model/Adam/Torch-private RNG/order/cursor/historyの完全なtrajectory digestは前後一致。optimizer.stepはguardし試行0。旧control案の4バッチも含め今回の実行総数8、更新総数0。

実サイズのfull checkpointを2世代fsync→atomic replace→directory fsyncし、不完全pendingが残った状態でcommitted世代から復旧。saved全体の完全一致を確認した。試験ファイルは専用一時ディレクトリだけで処理し、元重みを上書きしない。RAM-backed tmpfsを永続保存と偽らない。これは**更新前の保存/復旧**検証であり、新しい更新後のreplay一致ではない。
